# Дизайн autosave для страницы «Сайт»

## Цель

Убрать ручное сохранение черновика со страницы «Сайт» и привести редактирование команды, контактов, подвала и модалок к тому же autosave-поведению, которое уже используется в редакторе тура.

Публикация остаётся отдельным действием: autosave сохраняет только draft и никогда не меняет публичную версию самостоятельно.

## Текущий workflow

- Администратор открывает раздел «Сайт».
- UI загружает draft-документ и его revision для выбранного kind.
- Изменение поля меняет локальное состояние.
- Сейчас draft сохраняется только по кнопке «Сохранить черновик».
- Публикация отправляет сохранённую revision в `/publish`.
- Публичный сайт читает опубликованный snapshot из S3/CDN.

## Новый workflow

1. Поле изменено.
2. UI отмечает текущий kind как «Есть изменения».
3. Через 800 мс после последнего изменения запускается autosave.
4. Пока запрос выполняется, новые изменения не теряются и сохраняются следующим запросом.
5. После успешного PUT обновляются документ, revision и базовый snapshot.
6. Администратор видит confirmation box «Черновик сохранён».
7. Публичный сайт не меняется до явного нажатия «Опубликовать на сайте».

Для checkbox, сортировки, добавления и удаления используется тот же debounce 800 мс. Это исключает пачку запросов при нескольких последовательных действиях и соответствует существующему `useAdminAutosave`.

## Publish

- Кнопка «Сохранить черновик» удаляется.
- Кнопка «Опубликовать на сайте» остаётся.
- Если autosave ещё выполняется, publish ждёт его завершения.
- Если есть ошибка или конфликт revision, publish блокируется до решения проблемы.
- После успешной публикации показывается confirmation box «Изменения опубликованы».
- Autosave не считается публикацией.

## Feedback

Используется существующий `AdminToastProvider` / `useAdminToast`:

- autosave success: тихое уведомление «Черновик сохранён»;
- publish success: заметное уведомление «Изменения опубликованы»;
- save error: «Не удалось сохранить изменения» + действие «Повторить»;
- publish error: отдельное сообщение об ошибке публикации;
- revision conflict: предупреждение с предложением перезагрузить актуальный draft;
- permission error: понятное сообщение о недостаточных правах.

Toast не появляется на каждый ввод символа — только после фактического ответа API. Стабильный статус на странице дополнительно показывает `Сохраняем…`, `Черновик сохранён`, `Есть неопубликованные изменения` или `Опубликовано`.

## Состояние и границы

Autosave должен быть независимым для каждого kind: `team`, `contacts`, `footer`, `modal`. Переключение вкладки не сбрасывает локальные изменения и не запускает публикацию.

Для upload фотографии сначала завершается upload asset, затем изменённый team-документ проходит обычный autosave. При размонтировании страницы активный debounce отменяется; уже отправленный запрос не отменяется и должен корректно обновить состояние только при совпадении актуальной revision.

## Валидация и ошибки

- Схема CMS остаётся источником обязательности полей.
- Ошибка API не должна затирать локальный документ.
- `409 rev_conflict` переводит kind в состояние конфликта и останавливает autosave до ручной перезагрузки.
- `403 forbidden` отображается как ошибка прав.
- Пустые обязательные поля должны показываться рядом с полем и блокировать autosave до исправления.

## Тестовое покрытие

Добавить тесты для:

- debounce autosave после изменения каждого типа поля;
- отсутствия ручной кнопки сохранения;
- confirmation box после успешного autosave;
- повторной попытки после save error;
- ожидания autosave перед publish;
- confirmation box после publish;
- сохранения изменений при переходе между вкладками;
- остановки autosave на revision conflict;
- независимого состояния `team`, `contacts`, `footer`, `modal`.

## Критерии готовности

- Администратор меняет любое поле и не нажимает кнопку сохранения.
- В течение debounce draft сохраняется через существующий CMS API.
- Confirmation box подтверждает результат запроса.
- После перезагрузки страницы draft содержит последнее значение.
- Публичный сайт меняется только после публикации.
- При ошибке администратор видит причину и может повторить действие.
- Все изменённые сценарии покрыты тестами.
