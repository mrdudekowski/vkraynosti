# Клонирование тура: UI админки

## Цель

Дать редактору и администратору возможность создать новый тур на основе контента существующего тура и выбрать целевой сезон до запуска операции.

Клон создаётся backend как новый draft-тур с новым ID и уникальным slug. Выезды, бронирования и CRM-данные не копируются.

## Пользовательский workflow

1. Пользователь открывает меню действий конкретного тура в списке туров.
2. Выбирает действие «Клонировать».
3. Админка открывает диалог «Клонировать тур».
4. Пользователь выбирает целевой сезон.
5. Пользователь подтверждает операцию кнопкой «Клонировать».
6. Пока запрос выполняется, элементы формы блокируются, а кнопка показывает состояние загрузки.
7. После успешного ответа список туров обновляется, диалог закрывается, и админка автоматически переходит на страницу нового тура.
8. На странице нового тура показывается toast «Тур склонирован как черновик».

## Точка входа

Действие добавляется в существующее меню действий карточки тура (`AdminTourCard` / `AdminTourActionsMenu`). Глобальная кнопка и отдельный дублирующий экран не добавляются.

## Диалог

Используются существующие primitives админки:

- `AdminDialog` для оболочки и управления фокусом;
- `AdminSelect` для выбора сезона;
- `AdminButton` для действий;
- существующий toast-контекст для результата операции.

Содержимое диалога:

- заголовок: «Клонировать тур»;
- название исходного тура как read-only контекст;
- label «Целевой сезон»;
- select со всеми доступными сезонами;
- пояснение: «Будет скопирован только контент тура. Выезды и CRM-данные не копируются.»;
- кнопки «Отмена» и «Клонировать».

Целевой сезон не предвыбирается автоматически, чтобы пользователь явно подтвердил перенос. Кнопка подтверждения недоступна, пока сезон не выбран.

## API и состояние

В `src/admin/api.ts` добавляется функция:

```ts
adminCloneTour(id, targetSeason)
```

Она вызывает:

```text
POST /api/cms/tours/:id/clone
{ targetSeason }
```

Функция возвращает `{ document, meta }`. Из `document.id` берётся целевой маршрут редактора.

Локальное состояние контролирует:

- открытие/закрытие диалога;
- выбранный сезон;
- состояние запроса;
- сообщение об ошибке.

После успешного ответа порядок действий:

1. обновить данные списка туров;
2. закрыть диалог;
3. перейти на страницу нового тура;
4. показать success toast.

Если обновление списка не успело завершиться, переход всё равно выполняется по ID из ответа API; страница редактора сама загрузит новый draft.

## Ошибки и безопасность workflow

- `400 invalid_body` — показать «Выберите корректный сезон»;
- `404 not_found` — показать «Исходный тур не найден»;
- `422 source_media_not_found` — показать «Не удалось скопировать медиа исходного тура»;
- `401/403` — использовать существующий механизм сессии/permission error;
- остальные ошибки — «Не удалось клонировать тур. Попробуйте ещё раз».

Диалог остаётся открытым после ошибки, выбранный сезон сохраняется. Повторный submit блокируется на время активного запроса.

## Responsive и accessibility

- на desktop диалог имеет обычную компактную ширину операционной формы;
- на узких экранах контент укладывается в viewport без горизонтального overflow;
- все controls имеют видимые labels;
- фокус после открытия попадает в select, после закрытия возвращается на кнопку «Клонировать»;
- ошибка связана с формой и доступна скринридеру;
- кнопки имеют минимум 44px touch target;
- loading не меняет размеры диалога и не создаёт layout shift.

## Тестирование

Добавляются тесты на:

- наличие действия «Клонировать» в меню тура;
- открытие диалога;
- disabled-состояние submit без выбранного сезона;
- отправку `targetSeason` в API;
- loading и блокировку повторного submit;
- успешную навигацию на ID нового тура и success toast;
- отображение ошибки при отказе API;
- закрытие по отмене без запроса.

## Ограничения scope

В рамках UI не меняются:

- модель сезонов;
- backend-правила уникальности ID/slug;
- работа с выездами, бронированиями и CRM;
- редактор контента нового тура;
- существующие responsive-изменения `ScheduleWeekSplitLayout.tsx`.
