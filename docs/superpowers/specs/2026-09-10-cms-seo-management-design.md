# CMS SEO Management Design

## Goal

Добавить в CMS управляемые SEO-поля для туров и основных публичных страниц сайта, сохранив простой интерфейс для редакторов и существующую модель публикации.

## Scope

В первый этап входят:

- вкладка `SEO` в редакторе каждого тура;
- SEO-настройки главной и четырёх сезонных страниц в разделе `САЙТ`;
- перенос существующего SEO-поля тура в новую вкладку без потери данных;
- автоматическое формирование технических SEO-значений;
- отображение SEO-изменений в очереди и истории публикаций;
- публикация SEO тура через существующее право `canPublishTours`;
- публикация SEO страниц сайта через существующее право `canEditSiteContent`.

В первый этап не входят отдельное право `canPublishSeo`, ручное редактирование `robots`, `canonical`, Sitemap и OG Image, а также отдельный механизм отката.

## User experience

### SEO тура

Вкладка показывает только понятные редактору поля:

- SEO title;
- meta description;
- H1;
- предпросмотр поискового сниппета;
- подсказки о пустых, слишком коротких, слишком длинных и дублирующихся значениях.

OG Image всегда берётся из обложки тура. Если SEO-поле пустое, интерфейс показывает предупреждение, а публичный snapshot использует безопасное значение по умолчанию.

Редактор не видит и не меняет `robots`, `canonical`, приоритет Sitemap или Schema.org.

### SEO страниц сайта

Раздел `САЙТ` содержит фиксированный список публичных SEO-страниц:

- главная;
- зимний раздел;
- весенний раздел;
- летний раздел;
- осенний раздел.

Для каждой страницы редактируются только title, description и H1. Маршрут страницы фиксирован в коде и не вводится вручную.

## Data model

SEO тура хранится внутри документа тура:

```ts
type CmsTourSeo = {
  title?: string;
  description?: string;
  h1?: string;
};
```

Поле `seoDescription` сохраняется для обратной совместимости и мигрируется в `seo.description` при чтении/сохранении. Новые записи используют объект `seo`.

SEO страниц сайта хранится в отдельном документе:

```ts
type SiteSeoPage = {
  key: 'home' | 'winter' | 'spring' | 'summer' | 'fall';
  path: string;
  title?: string;
  description?: string;
  h1?: string;
};

type SiteSeoDocument = {
  kind: 'seo';
  schemaVersion: 1;
  pages: SiteSeoPage[];
};
```

Публичный ключ документа: `published/site-seo/document.json`. Draft и meta используют существующее разделение CMS-документов.

## Automatic technical values

Публичный frontend строит технические значения только из опубликованных данных:

- `canonical` — из фиксированного маршрута;
- `robots` — из статуса тура или типа страницы;
- OG title — из SEO title;
- OG description — из SEO description;
- OG image тура — из обложки;
- Sitemap — из разрешённых индексируемых маршрутов;
- Schema.org — из данных тура и страницы.

Правила индексации туров остаются прежними: `active` индексируется, `in_development` получает `noindex,follow`, `hidden` не попадает в Sitemap и не является публичной индексируемой страницей.

## Publication workflow

Изменение SEO тура считается изменением документа тура.

- только SEO-изменение: очередь показывает `Изменение тура`;
- контент и SEO одновременно: очередь показывает `Изменение тура и SEO`;
- публикация использует `canPublishTours`;
- публикация SEO тура не требует отдельного SEO-права и не обходится без обычных проверок публикации тура;
- SEO страницы сайта публикуется через `canEditSiteContent` и отображается как `Изменение SEO страницы`.

Если документ тура и SEO меняются одновременно, публикуется одна согласованная ревизия, а не два отдельных snapshot.

## Permissions

- редактор с правом редактирования может изменять SEO тура и страницы сайта в доступном ему разделе;
- `canPublishTours` разрешает публиковать тур вместе с его SEO;
- `canEditSiteContent` разрешает публиковать SEO главной и сезонных страниц;
- отдельное право `canPublishSeo` не создаётся.

## Publication history

История публикаций сохраняет автора, дату, draft- и published-ревизии и список изменённых полей. Отдельный rollback UI в первый этап не добавляется: возврат выполняется обычным редактированием и повторной публикацией.

## Validation and fallback

Сохранение не блокируется из-за пустого SEO-поля. Система:

- показывает предупреждение редактору;
- использует title тура/страницы как fallback для H1;
- строит title и description из существующих данных, если ручные значения отсутствуют;
- проверяет дубли на уровне очереди или диагностического отчёта;
- не публикует технически невалидный URL или произвольный маршрут.

## Testing

Нужно покрыть тестами:

- схему и обратную совместимость документов тура;
- схему фиксированных SEO-страниц;
- генерацию fallback-значений;
- определение изменённых SEO-полей;
- объединение контентного и SEO-изменения в одной записи очереди;
- права `canPublishTours` и `canEditSiteContent`;
- публикацию draft в `published/site-seo/document.json`;
- передачу опубликованных значений во frontend и Sitemap;
- запрет hidden/in_development туров в индексируемом Sitemap.

## Success criteria

После реализации:

1. Редактор изменяет SEO из отдельной вкладки тура.
2. SEO главной и сезонных страниц изменяется в разделе `САЙТ`.
3. SEO тура публикуется существующей кнопкой публикации и правом `canPublishTours`.
4. Одновременные изменения контента и SEO публикуются одной ревизией.
5. Публичный сайт использует опубликованные CMS-данные, а не draft.
6. OG Image тура всегда совпадает с его обложкой.
7. Robots, canonical и Sitemap формируются системой.
8. Старое поле `seoDescription` продолжает работать во время миграции.
